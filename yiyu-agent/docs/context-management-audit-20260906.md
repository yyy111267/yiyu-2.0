# 以渔上下文管理梳理（2026-09-06）

范围：本地工作区代码，包含本次会话新增的追问修复；不代表生产环境已部署。此次为代码链路梳理，未进行生产模型调用测量。

## 1. 两种“多轮”

- 一次研究内部多轮：取数、观察结果、推进计划、再取数、生成结论。ContextManager 主要管理这一层。
- 用户之间多轮：先“分析智谱”，再“为什么是100倍市净率”，再“你用的是哪一期净资产”。需要会话主题、上轮结论和证据来源连续保留。

当前第一层已有计划、证据筛选和预算机制；第二层刚接上最近历史文本，尚未形成跨请求的研究状态与证据恢复机制。

## 2. 每次模型调用实际收到什么

底层 core/llm.py 重新构建 system 和 user 消息；有工具的调用另附 tools schema。当前没有把整段对话以原生 user/assistant/tool 消息序列逐条传入。历史记录被序列化成 user 消息里的 JSON，工具证据摘要则进入 system 中的上下文区。

| 内容 | 来源与条件 | 用途 |
| --- | --- | --- |
| 宪法与约束 | prompts/constitution.md，文件存在时 | 产品边界与行为要求 |
| 矫正提示 | 定向召回、反偏见、方法纪律、取数纪律；部分依赖用户/方法信息 | 约束执行方式 |
| 表达风格 | 非 execution 阶段，当前加载 novice.md | 最终成文表达；尚未按用户水平动态分层 |
| Skill | 路由选出的当前技能 | 决定当前工作流；追问未必仍走 deep-research |
| Deep Research 执行合同 | assembler 的分阶段紧凑合同 | execution 和 synthesis 使用不同内容，并非每轮把完整 SKILL.md 全塞进去 |
| 能力包/行业框架 | 父 Skill 声明 + 已识别行业 + 当前阶段 | 通用方法、指标规则和相应行业方法；行业框架主要在综合阶段加载 |
| 当前实体与日期 | preloop 或本轮工具更新的 current_entity | 公司、证券代码、市场及当前日期 |
| 研究配方 | 画像派生的 research_recipe | 应算哪些指标、应补什么材料、适用估值方法等 |
| 当前研究计划 | ResearchPlan | 问题、状态、维度与取证要求 |
| 证据工作集 | 工具结果经过压缩、关联、排序和预算装箱 | 本轮能够看到的数据和来源索引 |
| 用户认知与底线 | 已加载的偏好、已确认认知目录、投资底线 | 表达偏好与待验证假设；条件加载，不是所有请求自动读取所有长期记忆 |
| 执行反馈 | 当前阶段、剩余步骤、上次准出失败原因、连续取数引导 | 下一轮该做什么、哪些内容要修正 |
| 最近对话文本 | 本次修复：同用户同会话最近 6 条，每条最多 4000 字符 | 理解追问所指的公司、数字和前文；不作为已核验事实 |
| 当前用户问题 | 当前请求原文 | 本轮目标，放在历史之后 |
| 工具定义 | 按阶段与未完成问题裁剪后的 tools schema | 当前允许调用哪些工具、如何传参；综合阶段不提供工具 |

代码入口：runtime/assembler.py::build / _load_skill_workflow / _build_context，runtime/loop.py::_react_loop / _synthesize_and_finish，core/llm.py。

## 3. Data Pack 到模型之间还有筛选层

应分清三个对象：

1. company_facts：前处理生成的公司事实，供画像、粒度、计划等使用。保存在 initial_context 中不意味着原封不动进入 Prompt；assembler 是显式挑字段，不是遍历整个 context 全量输出。
2. 统一行情数据包 MarketBundle：取数与计算复用的结构化数据，有版本、来源映射、缺字段等信息。
3. Evidence 工作集：取数/计算/网页等工具的结果进入观察记录与 EvidenceStore，再投影成模型本轮能看到的摘要。

当前压缩规则：对象优先字段、最多 24 个键；列表前 6 项；字符串前 800 字符；深度达到 3 后转为最多 240 字符的文本；EvidenceStore 最后再截到 1800 字符。原始数据仍留在运行态，模型看到的是摘要。

主链路工作集默认预算：execution 约 2200 个估算 token；synthesis 约 6000。估算使用约 2 字符/token，不是 tokenizer 精确计数。实际还受本次 input_token_budget 扣减影响。

执行阶段按未完成 P0 关联筛选，综合阶段放宽相关性筛选；相同摘要去重。排序考虑问题关联、来源类型和记录顺序。装箱时超过预算的证据不进入本轮。

这些规则能降低重复输入，但不能保证每个关键数字的完整计算依据都保留下来。例如 pb 数值可能留下，深层嵌套的来源、分子分母或口径可能被截断。当前“来源质量”是按工具类型分档的启发式，不能等同于逐字段真实性验证。

代码：runtime/context_manager.py，runtime/evidence_workspace.py，toolkit/market/research_data.py。

## 4. 一次研究与下一次追问之间如何衔接

一次研究内部：ContextManager 保留本请求 EvidenceStore，工具结果进入 observations；每轮重新选择证据，计划随 plan.update 更新，工具集也随问题缺口改变。

下一次用户请求：AgentLoop.run 新建 AgentState，并 reset ContextManager。上一轮 observations、研究计划和证据关联不会因 session_id 相同而自动恢复。

已修复的链路：前端固定会话 ID → API 按 user_id 和 session_id 读最近消息 → initial_context.conversation_history → PromptAssembler.user。此链路解决最近文本进入回答模型的问题。

仍存在的区别：

- API 路由只有 LLM 分支使用最近 3 条、每条前 200 字符；强规则分支会提前返回。
- preloop 仍接收本次原始问题和路由实体候选，没有统一接收会话主题/历史。匿名指代的研究型追问仍可能在回答生成之前遇到实体定位问题。
- 最终答案保存有 metadata/citations，但本次历史注入只取 role/content，没有恢复上轮引用清单、原始指标与计算链。
- SessionRepo 有 checkpoint 接口，详情 API 也可读取；当前 chat → AgentLoop 主链路没有接入这些检查点的保存/恢复。不能根据注释推断已具备完整断点续跑。
- MarketBundle 是按会话 scope 与证券键组织的进程内 LRU 缓存，最多 256 份；同进程可能复用，但跨实例、重启或淘汰后不保证存在，且缓存存在不会自动变成模型的证据工作集。

## 5. 现有预算机制的边界

ContextManager 主要控制计划、证据、工具部分，固定提示层使用预留估算。最终 system/user/tools 拼接完成后，loop 再估计输入成本，并在满足条件时进入综合收尾。

这不是全量 Prompt 的严格预算分配器：新加入的历史可接近 24000 字符，尚未在 prepare 阶段按实际长度统一扣除；过长历史会挤占研究额度。字符截断也不是语义摘要，可能丢掉较早的公司主题或截断上一条答案的计算说明。

已有 context_usage 审计记录选中证据、丢弃原因、问题证据映射和工具名称；llm_usage 记录用量。但尚缺“这次追问继承了哪个公司、引用哪一轮哪项指标、为什么选这些历史”的完整审计。

## 6. 建议的下一步（尚未实施）

优先补齐跨请求会话状态，并复用现有数据结构：

1. 请求进入时先识别延续、换公司、概念解释、质疑既有数字或重新研究。将当前主题与用户明确切换一并供路由、preloop 和回答模型使用；多公司歧义时澄清，不硬继承。
2. 保存可追溯的研究结果快照：公司标识、报告版本、关键结论、指标数值/单位/时点/口径、公式及输入、证据 ID、来源、缺口。原始证据按索引读取，不全量塞入历史文本。
3. 追问按需恢复相关证据：问 PB 就优先恢复 PB 及其分子分母、口径和来源；数据过期或缺失时明确重新核验。
4. 把 system、历史、状态、证据、tools 与输出预留纳入一次预算分配；保住当前问题与其计算依据，再压缩低相关历史。
5. 增加多轮评测：不重述公司、追问较早一轮、换公司、多个公司消歧、用户纠错、原数字无依据、指标过期、跨实例读取、跨租户隔离。

“为什么是100倍市净率”的目标上下文应包含：这次正在讨论哪家公司、上一条到底说了什么、这个数字对应的时点/单位/口径、用了哪些输入和公式、出处在哪里、是否存在缺失或口径错误。缺任何关键依据时，应指出并核查，不能只凭上一条回答继续解释。

当前判断：已经有请求内的 Context Engineering 基础；本次修复只是多轮文本接线。要支持稳定且可追溯的投研追问，还需要跨请求的会话主题与证据快照管理。
