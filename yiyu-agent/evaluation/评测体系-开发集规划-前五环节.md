# 评测体系：开发集规划（前五个环节）

状态：`draft v1`（2026-08-30）  
范围：01 意图路由、02 实体解析、03 商业模式分类、04 研究粒度、05 研究计划。  
用途：转成 `case_master` 与 `fixture_registry` 两张 CSV 的设计底稿；本文件不修改现有 Case 或代码。

## 一、这份文档的意义

这一步不是为了凑 Case 数量，而是把每个环节的产品合同写成开发者能运行的测试：开发前知道什么叫正确，开发中能定位具体失败环节，开发后能判断是否允许进入下一个环节。

统一方法：

```text
列出行为分支 → 选代表案例 → 固定输入/数据/上下文 → 定义结构化断言
→ 先跑出现状缺口 → 开发 → Stage 全绿 → 跑关联 E2E/Safety → 晋级
```

本批用例均是单环节开发规划：通常先标记为“开发集 / 不进回归 / 单环节测试 / 草稿”；明确属于产品红线的题直接标记为“安全集”。功能合同稳定后再转为功能集，其中的代表题标记为“候选核心”，经过稳定运行后才进入回归集。

## 二、表格字段约定

下列五张表使用统一的 16 个中文字段：

```text
用例ID,案例名称,被测对象,内容性质,回归角色,测试层级,场景类型,生命周期,
数据快照ID,Fixture固定内容,Mock行为,输入,预期路由与技能,预期过程,
预期终态与断言（hard=必过项，全过才算过；soft=加分项，不抵失败）,评分标准ID
```

其中“输入”“预期过程”“预期终态与断言”转 CSV 时存 JSON。为了让 Markdown 可读，本稿使用简写；转换时再机械转成 JSON，不改变含义。

## 三、01 意图路由

### 3.1 为什么测

路由决定请求进入轻回答、深度研究还是产品边界。错误路由会让后续全部工作失去意义，也会造成不必要的 LLM/Tool 成本。

### 3.2 打算怎么测

覆盖正常轻答、明确研究、多标的、模糊输入、连续状态、越界请求、注入混合文本和 LLM 分类失败。规则可判定的路径固定为零 LLM、零业务 Tool。

## 四、02 实体解析

### 4.1 为什么测

实体解析决定公司、市场和证券代码。它的高风险不是“没找到”，而是“自信地找错”：研究 A 股却取到港股、刚上市公司因本地表滞后被判不存在，或模型凭记忆编出代码。

### 4.2 打算怎么测

采用“本地主数据 → 远端权威主数据 → LLM 只归一名称 → 主数据复核”的目标链路。LLM 不能成为证券代码的权威来源。新上市公司用合成 Fixture 模拟，不依赖真实当天上市名单。

## 八、前五环节完成后的统一验收

只有同时满足以下条件，才进入第六至第十一个环节的 Case 设计：

1. 每条用例的 16 个字段齐全，复杂字段可无损转成 JSON。
2. 每个 Fixture 有明确固定数据、Mock 行为和版本；不得依赖当天真实市场数据。
3. 每个环节至少覆盖 normal、boundary、exception/degradation；stateful、安全、性能按实际风险加入。
4. 所有 Hard 断言可由结构化结果或 Trace 判定，不依赖自由文本全文相等。
5. 规则/纯函数 Case `K=1` 全绿；LLM Case 完成 `K=3` 稳定性检查。
6. Safety Hard Fail 为 0 容忍；Soft 分不能抵消 Hard 失败。
7. 环节之间的输入输出合同对得上：路由候选 → 实体 → 分类 → 粒度 → 计划。

本批规划共 42 条：意图路由 8、实体解析 12、商业模式分类 6、研究粒度 7、研究计划 9。数量只是覆盖结果，不是固定配额；评审时可以合并重复题，也可以针对确认的分支缺口补题。
