状态：`draft v1`（2026-08-30）  
范围：06 指标公式、07 认知抽取、08 准出硬规则、09 事实构建、10 公司画像、11 研究循环、12 指标计算 Skill。  
用途：作为转成 CSV、Fixture 和可执行用例的设计底稿；本文档不修改业务代码。

## 一、数据快照ID是什么

数据快照ID是一套“固定考场”的唯一引用，例如 `fx_facts_v1`。它不是用例编号，而是指向该题执行时的确定性数据、上下文和外部依赖响应。

它用来：

1. 保证今天和下周跑的是同一份事实，结果可复现。
2. 分数变化时，能区分是代码变了还是“考场”变了。
3. 让多条用例共享同一份数据，不在主表里重复维护。
4. 通过 `v1`、`v2` 保留版本，历史运行仍能还原。

“Fixture固定内容”和“Mock行为”是快照的人类可读摘要；执行时以“数据快照ID + 版本”定位完整数据。快照内容发生业务性变更时应升版，不应静默覆盖。

## 二、统一约定

全部使用你确认的 16 个中文字段。用例ID按环节简化：`M` 指标公式、`K` 认知、`S` 准出、`F` 事实、`H` 画像、`L` 循环、`T` 指标工具。

- “内容性质”表示用例测的是功能还是安全红线，不等于它当前存放在哪个集合。
- “候选核心”只表示日后可能进回归集；当前仍是开发用例。
- Hard 断言必须能由结构化输出或 Trace 判定；Soft 不能抵消 Hard 失败。

## 十、整体验收与下一步

本文档规划 66 条：指标公式 8、认知抽取 11、准出 8、事实构建 5、公司画像 6、研究循环 18、指标 Skill 10。与前五环节的 42 条合计 108 条。数量不是硬指标，应以“每个独立代码分支是否有代表题”判断增删。

进入“转 CSV 和实现 Fixture”前，需同时满足：

1. 108 条用例都能对应一个真实代码分支，无纯粹凑数量的题。
2. 每条的 16 个字段完整，数据快照ID能唯一找到固定数据和 Mock 行为。
3. 每个 Hard 断言都能被机器从输出或 Trace 判定，不使用自由文本全文相等。
4. 纯函数和固定 Mock 题 `K=1`；真正依赖 LLM 随机性的题 `K=3`，安全和候选核心题要求 `pass_all@3`。
