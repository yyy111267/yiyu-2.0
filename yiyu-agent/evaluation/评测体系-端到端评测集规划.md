# 评测体系：端到端评测集规划

状态：`draft v1`（2026-08-31）  
范围：从真实用户输入开始，经过路由、实体、事实、画像、计划、多 Tool 研究循环和准出，直到用户收到最终结果。  
用途：作为端到端 CSV、场景级 Fixture、执行器扩展和发版回归题的设计底稿；本文档不修改业务代码。

## 一、为什么单环节全绿仍然不够

单环节 Case 验证的是“一个零件在固定入口下是否符合合同”；端到端 Case 验证的是“用户交给产品的任务最终是否真的完成”。

单环节无法充分暴露的问题包括：

- 上一环节输出字段合法，但下一环节理解错了。
- 每个 Tool 都能单独成功，但 Agent 不知道先调谁、为什么调、调几次。
- Tool 失败后不会改路、重试风暴、降级后又把缺数当真数。
- 中间状态都正确，但链路没有走到最终交付，或只输出了流程日志。
- 多轮历史、重复事实和 Tool 全量返回持续进入 Prompt，导致上下文膨胀和语义漂移。
- 某次的错误实体、失败结果或他人会话状态污染了当前任务。
- 功能最终可以跑完，但首字延迟、总耗时、token 或 Tool 调用数已经不可接受。

因此，端到端题不能只检查“最终答案里有没有几个关键词”，而必须同时验收三层：

```text
任务终态：用户的目标是否真正完成
链路过程：路由、Tool、状态、证据和降级是否合理
系统约束：延迟、token、调用数、上下文和安全是否越界
```

## 二、端到端与环节 Case 的分工

| 维度 | 单环节 Case | 端到端 Case |
| --- | --- | --- |
| 输入 | 直接给函数或环节 schema | 给真实用户语句、会话历史和用户状态 |
| 被测对象 | 某个函数、Tool 或 Agent 环节 | 整条产品链路及各环节交界 |
| 主要问题 | 这个环节算得对吗 | 用户任务完成了吗，为什么成功或失败 |
| Tool 断言 | 精确名称和参数 | 必要 Tool、禁止 Tool、部分顺序、重复次数和失败策略 |
| 结果断言 | 字段、枚举、数值 | 业务终态、证据覆盖、语义一致性和用户可用性 |
| 性能断言 | 单次函数耗时 | TTFT、总耗时、全链路 token、Tool 调用数和上下文增长 |
| 归因 | 定位到函数分支 | 先定位失败阶段，再回到对应环节 Case 复现 |

## 三、现有 E2E 执行器在落地前需补的契约

1. **真实路由**：当前 runner 将 Case 的 `skill` 作为 `explicit_skill` 传给路由。需增加“是否强制 Skill”开关；默认 E2E 必须从用户语句真实路由。
2. **场景级 Fixture**：当前 live 路径直接装配真实 MarketData 和 WebSearch。需支持一条 Case 注入整段 Tool 响应脚本，否则无法稳定复现失败、慢响应和冲突数据。
3. **多轮输入**：现有 schema 只支持一条 message。需支持 `turns[]`、每轮预期状态和轮次间持续的 session_id。
4. **预期降级**：当前 live 汇总将所有 `degraded=true` 统一判失败。需允许 Case 声明 `expected_degraded=true`，因为安全降级并完成交付本身可以是正确终态。
5. **过程断言**：需从“只有 must_do 语义判分”扩展为可执行的必调 Tool、禁调 Tool、偏序关系、最大次数、参数断言和观测回写断言。
6. **资源和上下文断言**：需增加 `prompt_tokens_by_step`、`context_bytes_by_step`、`dedup_ratio`、`retry_count`、`useful_tool_call_ratio`、`checkpoint_restore` 等指标。
7. **用例隔离**：并发跑批中每条 Case 必须有独立 AgentLoop、session、cache namespace 和 Mock 脚本，并专门评测是否串数。
8. **报告留档**：当前固定文件名会覆盖报告。正式运行应写入 `reports/runs/<version>-<timestamp>.jsonl`，同时保留 environment、fixture、prompt、model 和 commit 指纹。

## 四、统一指标和门槛

| 指标 | 轻回答 | 深度研究 | 判定 |
| --- | --- | --- | --- |
| 有最终答案 | 100% | 100% | 包括安全降级答案，不允许空结果 |
| TTFT 目标 / 硬上限 | `<=3s / <=8s` | `<=30s / <=75s` | 目标超限警告，硬上限超限失败 |
| 总耗时目标 / 硬上限 | `<=15s / <=30s` | `<=90s / <=130s` | 与当前生产 research=120s 预算对齐 |
| token 目标 / 硬上限 | `<=5k / <=10k` | `<=35k / <50k` | 不能依靠超预算换取通过 |
| Tool 调用目标 / 硬上限 | `0–2 / <=4` | `<=12 / <36` | 具体 Case 可设更严上限 |
| 同参数重复取数 | 0 | 0 | 前次失败且有 retry_reason 时最多允许 1 次 |
| 状态机违规 | 0 | 0 | 任一越阶都失败 |
| 安全 Hard Fail | 0 | 0 | 复用独立安全集，不在功能平均分中稀释 |

单条 Case 同时验收任务终态、链路过程和系统约束。确定性 Mock 题 `K=1`；真实 LLM 题 `K=3`；冻结核心题要求 `pass_all@3=true`。任务终态 Hard Fail、空答案、链路未完成、状态串扰和安全失败必须为 0。

上述是 v1 可执行阈值，不是永久 SLA。应保留每次运行的连续数值，累积 5–10 次稳定基线后再用 P50/P95 调整阈值。

## 六、这些题如何执行，而不是只停在表格里

### 6.1 两种运行模式

| 模式 | 目的 | 数据与依赖 | 运行频率 | 判定重点 |
| --- | --- | --- | --- | --- |
| 确定性场景模式 | 定位系统逻辑问题，回答“为什么失败” | 固定 Fixture、脚本化 Mock、固定 seed 与环境 | PR 开发期和每日 | 路由、调用顺序、参数、重试、状态、预算、终态 |
| 真实链路模式 | 回答“面对真实世界还能不能工作” | 固定输入，真实模型和允许联网的真实 Tool | 每周、发版前 | 成功率、P50/P95 延迟、稳定性、内容质量与外部波动 |

不能只跑 Mock，因为那会漏掉真实供应商延迟和模型波动；也不能只跑真实依赖，因为失败后很难判断是代码回归还是外部数据变化。相同 Case 可以有两种执行 profile，但仍使用同一个用例ID。

### 6.2 自动判与人工判的边界

机器自动断言：

- 路由和技能、实体 ID、Tool 名称、参数、状态码、调用次数与偏序。
- 是否发生重复调用、越阶、无限重试、串会话和链路未结束。
- TTFT、总耗时、逐步 token、上下文峰值、Tool 调用预算。
- 固定 Fixture 下的数字、单位、日期、来源 ID 和任务覆盖字段。

人工复核：

- 最终结论是否真正回答用户，而非只是“有输出”。
- 事实、推断和建议的边界是否清楚。
- 冲突证据、复杂上下文和降级说明是否合理。
- 表达结构、信息取舍和用户是否能据此采取下一步行动。

LLM Judge 可用于生成待复核分数或检查 Key Points，不应覆盖确定性 Hard 断言，也不应单独决定发版。

### 6.3 每次运行必须输出的机器可读字段

建议每个 Case 每次运行输出一行 JSONL，至少包括：

```json
{
  "run_id": "版本-时间戳",
  "case_id": "EE01",
  "attempt": 1,
  "environment_fingerprint": "commit/model/prompt/tool",
  "fixture_fingerprint": "fixture-commit-or-hash",
  "seed": 42,
  "route": "research",
  "skill": "stock_research",
  "terminal_state": "completed",
  "expected_degraded": false,
  "tool_calls": [],
  "hard_assertions": [],
  "soft_scores": {},
  "ttft_ms": 0,
  "duration_ms": 0,

  "failure_reason": null,
  "machine_pass": true,

```

`failure_stage` 使用固定枚举：`routing`、`entity`、`preloop`、`tool_selection`、`tool_execution`、`state`、`context`、`budget`、`finalization`、`safety`、`judge`、`infrastructure`。这样报告既能说当前质量，也能聚合问题发生在哪里。

## 七、通过标准与进入下一阶段的条件

第一阶段先实现 18 条高价值 Case：EE01、EE02、EE04—EE08、EE10、EE12—EE16、EE18、EE23—EE25、EE27、EE30。选择依据是它们覆盖主链路、常见失败和最危险的系统性问题，不需要一开始就把所有复杂能力开发完。

开发期通过条件：

- 确定性场景模式下，18 条 Case 的 Hard 断言 100% 通过。
- 任何 Case 都有最终答案或明确的预期降级终态；空响应和未结束链路为 0。
- 重复调用、状态越阶、跨 Case 污染、安全红线为 0。
- 资源指标不越各 Case 的硬上限。
- 每个失败都能自动归入一个 `failure_stage`，不能只有“总分下降”。

基线稳定后再补齐其余 18 条，并对核心题跑真实链路 `K=3`。连续 3 次版本运行通过、业务关键路径覆盖完整且指标波动进入稳定区间后，才把约 12—18 条“核心题候选”冻结复制进 regression；以后发现的线上或历史 badcase 再作为哨兵题补入。安全端到端题仍由独立 safety 集管理并要求全绿，不与本功能集平均分混算。

## 八、开发者使用这套 E2E 的最短闭环

```text
开发或修改功能
  → 先跑对应单环节 Case，确认局部合同
  → 跑受影响的确定性 E2E Case，确认跨环节闭环
  → 根据 failure_stage 回到具体环节修复
  → 发版前跑冻结 regression + safety
  → 定期跑真实链路并观察 P50/P95、pass_all@3 和人工复核结果
  → 稳定 badcase 升格为回归哨兵
```

端到端集不是另一份“更大的功能题库”，而是专门验证零件连接之后是否仍能完成真实用户任务。单环节题负责快速定位和便宜反馈，端到端题负责发现组合故障与业务终态问题，两者缺一不可。
