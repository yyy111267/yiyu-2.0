# Fetch Planner 产品与实现方案

## 第一部分：用产品语言理解它

### 它解决什么问题

字段注册表像“可售商品目录”：系统认识哪些指标、每个指标是什么意思。

来源映射表像“供应商名单”：每个指标理论上可以向谁采购，主源和备源是谁。

Fetch Planner 像“本轮采购单”。它不重复购买已经有的数据，也不盲目相信过期数据；它会结合用户这次的问题、当前会话已经拿到的数据、缓存和供应商状态，决定这次真正要发出的最小请求。

它的目标可以概括为一句话：用尽量少、尽量快的结构化请求，补齐本轮回答真正缺少的数据。

### 为什么每轮都要重新规划

同一个问题在不同时间出现，正确计划可能完全不同。

第一次对话没有数据，需要从零取数。第二轮对话可能已经有价格和估值，只需补财报。几分钟后价格过期，需要刷新行情；一份已经确认报告期的年报仍可继续使用。某个主源熔断时，Planner 应直接把健康备源提前，避免等待一个已知不可用的接口。

所以 Planner 保存的不是一份长期固定计划，而是每轮根据现场状态生成的一次性计划。

### Planner 的五个输入

1. 用户本轮需要的字段。可以由 Agent 直接点名，也可以从 PE、ROIC 等指标自动拆出基础字段。
2. 当前会话的 Data Pack。这里保存前几轮已经获得的字段、值、报告期、来源和取数时间。
3. 持久缓存的字段状态。缓存层告诉 Planner 某个字段是否命中、是否新鲜；Planner 不自己管理数据库。
4. 标的市场。A 股、港股、美股的接口能力不同，未经验证的跨市场能力不能使用。
5. Provider 当前状态。正常、性能下降、限流、熔断或停用都会改变本轮顺序。

### 它怎样做决定

Planner 按下面的漏斗逐个处理字段：

```text
本轮需要字段
    ↓
Data Pack 中有新鲜且同报告期的值？── 有 → 直接复用
    │
    没有
    ↓
缓存中有新鲜且同报告期的值？────── 有 → 直接复用
    │
    没有
    ↓
Registry 是否登记？─────────────── 没有 → unregistered
    │
    有
    ↓
Source Mapping 有当前市场/时间配方？ 没有 → not_supported
    │
    有
    ↓
过滤熔断、停用、限流的来源
    ↓
正常来源优先，降级来源靠后
    ↓
相同真实请求合并为一个批次
    ↓
生成主源步骤 + 条件备源步骤
```

### “最少调用”不是按 Provider 名字粗暴合并

营业收入和资本开支虽然都可能通过 AKShare 访问，但前者来自利润表，后者来自现金流量表。这是两个真实请求，不能写成一次“AKShare 获取 revenue、capex”。

Planner 只合并请求地址、参数模板和报告类型相同的字段。例如营业收入、净利润、营业成本都在新浪利润表中，它们可以合并为一次调用；资本开支单独形成现金流量表调用。

这使计划既省请求，又能真正执行。

### 用用户示例看一次规划

本轮请求：`price、pe_ttm、revenue、capex`。

当前 Data Pack 已有新鲜的 `price、pe_ttm`。Planner 的产品结果是：

```text
直接复用：price、pe_ttm
本轮补取：revenue、capex

第一批：AKShare → 新浪利润表 → revenue
第一批：AKShare → 新浪现金流量表 → capex

如果 revenue 主源失败：按 Source Mapping 尝试 WeStock，再尝试东财利润表
如果 capex 主源失败：尝试东财现金流量表
所有结构化来源失败：把相应字段列入联网搜索候选
```

两个第一批请求相互独立，可以由执行器在限流允许时并行；同一来源明确禁止并发时必须串行。

### 多轮对话中的缓存和上下文

会话 Data Pack 是“这次研究已经知道什么”的结构化事实库，按会话和标的隔离，并带版本号。持久缓存负责跨会话复用和过期管理。

建议每条字段最少保存：标准字段名、值、单位、报告期、来源、原始字段名、数据时间、取数时间、状态和证据 ID。需要特别区分“数据截至时间”和“什么时候取到”：2025 年报的报告期是 2025-12-31，但可能在 2026-03-30 才被系统获取。

给大模型注入上下文时，不要把完整接口响应反复塞进窗口。只注入本轮问题需要的字段、口径、报告期、来源、Data Pack 版本以及仍缺失的字段。原始响应保留在数据层供追溯。

前几轮已经算出的指标也可以复用，但必须记录它由哪个 Data Pack 版本计算。只要底层 Data Pack 升级，旧计算结果就不能直接沿用，应使用新字段重新计算。

### 新鲜度规则

当前默认规则是：行情 5 分钟，未指定报告期的“最新财报”1 天。缓存层显式给出 fresh/stale 时，以缓存层为准。

指定报告期的数据按报告期复用，不按年龄淘汰。例如用户明确要 2025 年报，已保存的 2025-12-31 数据可以继续使用。但旧 Data Pack 只有“2025”时，只能安全对应 2025 年报，不能猜成 2025 年三季报。

这些默认值以后应按业务场景配置。例如盘中盯盘可以把行情缩短到 30 秒，长篇基本面研究可以适当放宽。

### 失败时怎样继续

Planner 会提前生成条件备源步骤，但执行器只有在主源失败、字段为空或报告期不匹配时才执行。一次请求返回成功不代表字段成功：缺列、空值、错误单位和错误报告期都算该字段未满足。

所有结构化配方用尽后，该字段进入白名单联网搜索候选。搜索不是 Planner 自己执行；它给搜索执行器一个明确的字段、标的、报告期和口径，避免宽泛搜索。搜索仍失败时，最终答案诚实说明缺失。

### 产品上怎样衡量 Planner 做得好不好

- 复用率：本轮请求中有多少字段直接由 Data Pack 或缓存满足。
- 请求压缩率：逐字段请求数与合并后真实调用数的差距。
- 首源命中率：第一来源直接满足字段的比例。
- 备源挽回率：主源失败后由备源补齐的比例。
- 字段满足率：最终得到正确字段、正确报告期和正确口径的比例。
- P95 规划后取数耗时：不能只看接口成功率。
- 错配率：有数字但字段、单位或报告期错误，这是比“取不到”更严重的指标。
- 搜索兜底率：过高说明结构化能力不足或来源健康异常。

## 第二部分：代码怎样实现

### Planner 的边界

`fetch_planner.py` 负责纯决策：读入状态，输出计划。它不发网络请求、不写缓存、不把字段算出来，也不调用搜索。

执行器负责按计划调用并校验返回；缓存层负责存取与 TTL；Provider Guard 负责限流、超时和熔断；Research Data 负责会话内版本化合并；Source Mapping 负责静态路由。

边界清楚后，Planner 可以用固定输入做离线测试，不需要每次联网。

### 输入接口

`plan_fetch` 支持：

- `symbol / market`：确定市场能力边界。
- `metric_ids / requested_fields / field_groups`：本轮需求。
- `current_data`：MarketBundle 或字段字典；省略时可按 symbol 读取当前会话 Research Data。
- `cache_fields`：缓存层已经读取并标准化的字段状态。
- `provider_status`：可按 Provider 或具体接口 audit key 提供状态。
- `freshness_seconds / now`：便于按场景配置和确定性测试。

为了兼容现有调用，不带字段需求时仍保留旧的 snapshot、fundamentals、news 全量组件计划。

### 输出接口

`FetchPlan` 同时给产品层和执行层使用：

- `reusable_fields`：直接复用，不发请求。
- `reusable_metrics / metrics_to_compute`：哪些计算结果可直接沿用，哪些需要基于本轮 Data Pack 重算。
- `stale_fields`：已有但过期或报告期不符。
- `fields_to_fetch`：本轮结构化取数目标。
- `unsupported_fields / unregistered_fields`：静态能力缺口。
- `provider_blocked_fields`：有路由，但当前所有来源都不可用。
- `steps`：可执行批次，包含调用顺序、是否条件执行、Provider、实际上游、请求模板、目标字段、原始列名、预算和数据新鲜度类型。
- `web_search_candidates`：结构化能力不存在或耗尽后可以交给搜索的字段。
- `status`：`satisfied / ready / partial / blocked`。

`field_sources` 和 `source_mapping` 保留，用于兼容当前 MarketBundle 和诊断展示。

### 执行器怎样消费计划

1. 先把 `reusable_fields` 从 Data Pack 放入本轮结果。
2. 执行所有 `attempt=1` 的步骤；只有真实请求模板相同的字段一起取。
3. 对每个字段校验非空、类型、单位、报告期和证券代码。
4. 每得到一个字段就立即写入新 Data Pack 版本，并从缺口集合移除。
5. 仍缺失的字段才执行 `attempt=2`，依次类推。
6. 把失败写回 Provider Guard；如果状态变化或得到部分数据，再运行一次 Planner。
7. 结构化链耗尽后，仅把仍缺字段交给白名单搜索。

这一实现允许“边取边缩小计划”，不会因为某个字段失败而重取同一批已经成功的字段。

### 缓存层还需要补的一项元数据

当前 MarketBundle 已经有报告期和部分 `fetched_at`，但财报缓存最好明确区分：

- `period`：数据属于哪一期。
- `data_as_of`：上游数据截至时间。
- `fetched_at`：本系统何时取得。
- `expires_at`：缓存何时需要刷新。

Planner 当前兼容已有结构；当缓存层补齐这些字段后，只需把标准化结果传入 `cache_fields`，无需改规划算法。

### 当前尚未跨越的层

Source Mapping 已经细化到真实请求模板，但旧 Provider 仍以“整张快照/整套财报”方式工作。Planner 现在能够生成完整字段级计划，现有 MarketData 执行器还没有逐条消费 `steps`。

下一步接执行器时，应以 `steps` 为唯一调用依据，并在执行后重跑 Planner。直接让旧执行器只看 `components`，会丢失具体接口、列名、报告期和条件备源信息。
