## 1. 产品背景与用户问题

### 1.1 产品背景

个人投资者在研究一家陌生公司时，通常需要从财报、公告、行业资料、新闻和社区观点中自行筛选信息。信息分散、口径不一，容易出现以下问题：

- 不知道应先研究哪些问题，研究路径随意；
- 收集了大量材料，却无法形成有依据的判断；
- 事实、估算和观点混在一起，难以验证；
- 只寻找支持自己已有观点的信息，忽略反证；
- 每次研究都从零开始，个人判断方法难以沉淀和复用。

以渔希望帮助用户完成一轮结构化公司研究，并在用户主动确认后，把可复用的判断方法沉淀为个人认知。

### 1.2 待验证的产品假设

当前以下判断仍属于产品假设，需要通过访谈和内测验证，不视为已经成立的事实：

1. 目标用户愿意等待一次相对完整的 Agent 公司研究，而不只需要即时问答；
2. 带来源、假设和反证的研究结果，比普通长文本报告更能帮助用户形成判断；
3. 用户愿意确认少量高质量认知，并在后续研究中继续使用；
4. 个人认知的正确复用能够形成区别于通用问答产品的持续价值。

### 1.3 产品价值锚点

产品优化的是用户的研究和决策过程，不承诺投资结果。

一次有价值的研究应帮助用户说清：

- 公司如何赚钱，价值由什么驱动；
- 当前判断由哪些事实和假设支撑；
- 最值得关注的风险和反证是什么；
- 哪些问题还无法回答；
- 出现什么新证据时，应当修改当前判断。

产品不预测短期涨跌、不承诺收益、不代替用户作最终买卖决定。

## 2. 目标用户与核心场景

### 2.1 目标用户

MVP 面向具备以下特征的个人投资者：

- 有基础投资经验，理解 PE、现金流、护城河等常见概念；
- 会阅读部分公司资料，但缺少稳定、系统的研究路径；
- 正在研究一家具体公司，希望形成有证据的基本面判断；
- 接受产品不预测涨跌、不提供确定性买卖指令的边界；
- 愿意检查、修正或沉淀自己的判断方法。

“投资 3—5 年”可作为招募首批用户的参考条件，不作为产品准入限制。用户是否符合目标人群，应以其实际研究行为和需求判断。

### 2.2 非目标用户

MVP 不重点服务以下需求：

- 寻找短线买卖点或确定性收益预测；
- 全市场自动选股；
- 量化回测、自动交易或模拟交易；
- 组合仓位配置；
- 实时盯盘与事件推送；
- 只需要未经解释的单一买卖结论。

### 2.3 核心场景

#### 场景 A：首次完整研究

用户对一家上市公司产生兴趣，希望系统了解其生意、财务、竞争优势、风险与估值，但不知道如何开始。

预期结果：用户获得一份有明确研究倾向、证据来源、关键假设、反证信号和信息缺口的公司研究结果。

#### 场景 B：专项问题研究

用户已经了解公司背景，只想深入研究一个会显著影响判断的问题，例如“现金还能支撑多久”“毛利率为什么下降”或“游戏业务的护城河是否减弱”。

预期结果：Agent 围绕该问题制定更小的研究范围，不强制生成完整七维报告，并清楚说明专项结论的适用边界。

#### 场景 C：基于个人认知继续研究

用户此前确认过一条可复用的投资认知，例如“提价只是检验定价权的信号，不能单独证明护城河”。研究新公司时，系统将其作为待验证假设使用。

预期结果：Agent 明示引用该认知，验证其在当前公司的适用条件，而不是直接复制旧结论。

### 2.4 暂不支持的核心场景

- 同时比较两家或多家公司；
- 未上市公司深度研究；
- ETF、基金、指数和加密资产研究；
- 持仓自动追踪、财报自动推送和逻辑变化预警；
- 交易复盘和组合构建。

用户提出多标的比较时，MVP 应说明当前仅支持单标的，并允许用户选择其中一家开始研究。

## 3. MVP 产品范围与优先级

### 3.1 标的覆盖范围

MVP 研究对象为能够唯一映射至证券代码的 A 股或港股上市公司。

首批重点保障以下行业：

1. AI 软件与大模型；
2. 半导体与 AI 算力；
3. 机器人与高端制造；
4. 消费品牌与成熟制造。

其他 A 股、港股上市公司可以进入通用研究流程，但如果缺少适用的行业研究方法或关键数据，应降低研究深度并显式说明限制。首发前应根据真实数据可用性验证，形成最终支持清单。

### 3.2 任务类型

MVP 支持三种输入处理方式：

|类型|触发条件|交付|
|---|---|---|
|轻回答|概念解释、单一事实、单点指标查询|单轮回答，不生成完整研究任务|
|完整研究|用户明确要求研究、深度分析或点击“生成完整研究”|完整公司研究结果|
|专项研究|用户提出一个需要多步取证的重要问题|围绕该问题的专项结论|

用户只输入公司名或证券代码时，默认先返回简要识别结果和可继续操作入口，不自动启动耗时较长的完整研究。

### 3.3 功能优先级

|优先级|能力|优先理由|
|---|---|---|
|P0|正确识别并确认研究对象|错误标的会使全部研究失效|
|P0|完整研究与专项研究闭环|构成 MVP 的核心交付|
|P0|证据来源、口径和不确定性展示|构成可信研究的最低要求|
|P0|任务状态、失败降级和部分交付|保证任务能够有序结束|
|P0|用户修改、暂停和取消研究|保证用户在长任务中保持控制权|
|P0|认知逐条确认后入库|构成认知陪练的最小闭环|
|P0|认知查看、编辑和删除|保证用户能够管理个人资产|
|P1|跨会话续研与完整上下文恢复|提升长任务和复访体验|
|P1|个人输出偏好自动记忆|提高个性化，但需先完成知情与关闭机制|
|P1|更多行业专用研究方法|扩展覆盖面|
|P2|多标的比较、持仓追踪和交易复盘|属于后续独立场景|

### 3.4 MVP 输出边界

允许输出：

- 对生意质量、财务质量、护城河、管理层、风险和估值前提的明确研究倾向；
- 支持和反对当前研究论点的证据；
- 判断成立的条件和反证信号；
- 当前价格隐含的主要市场预期；
- 用户下一步值得补充验证的问题。

禁止输出：

- “一定上涨”“稳赚”等收益承诺；
- 确定性的买入、卖出、加仓或清仓指令；
- 个性化仓位比例和具体交易节奏；
- 缺少可靠依据的目标价或精确预测。

“研究倾向”描述公司和当前论点的证据状态，不替用户作交易决定。

## 4. 产品整体流程

### 4.1 首次完整研究主流程

1. 用户输入公司名称、证券代码或明确的研究请求；
2. 系统识别研究对象；存在歧义时由用户选择；
3. 系统确认研究类型，并展示本次研究范围摘要；
4. Agent 开始研究，向用户展示概括性阶段和进度；
5. 用户可以继续补充问题、调整重点、暂停或取消；
6. Agent 完成取证后执行研究充分性和引用检查；
7. 系统根据实际完成情况交付完整结果或部分结果；
8. 系统提出少量候选认知，由用户逐条确认、修改或拒绝；
9. 研究结果和经确认的认知进入用户历史记录。

### 4.2 专项研究主流程

1. 用户提出一个具体研究问题；
2. 系统确认公司实体和问题范围；
3. Agent 围绕该问题开展多步取证；
4. 系统交付专项判断、证据、限制和下一步验证方向；
5. 如用户需要，可从专项研究升级为完整研究，并复用已核实资料。

### 4.3 用户参与原则

- 默认由 Agent 自主推进，不要求用户先确认完整研究计划；
- 研究开始时向用户展示简化的研究范围，用户可以修改；
- 能通过公开信息可靠解决的问题，由系统自行处理；
- 会改变研究对象、核心范围或结论方向的信息，系统必须向用户确认；
- 用户不参与认知确认，不影响本次研究结果的交付。

## 5. 功能详细设计

### 5.1 研究入口与任务路由

#### 功能目标

识别用户是需要即时回答、完整研究、专项研究，还是提出了当前能力范围之外的请求。

#### 产品规则

1. 明确的完整研究请求直接建立研究任务；
2. 需要多步取证才能回答的具体问题建立专项研究任务；
3. 概念和单点事实查询走轻回答；
4. 轻回答应提供“生成完整研究”入口，并复用已识别的公司；
5. 连续追问是否主动建议升级研究属于体验优化，不作为 MVP 硬规则；
6. 边界外请求不建立研究任务，应解释限制并提供可支持的替代问题。

#### 验收要点

- 用户明确说“研究一下贵州茅台”时创建完整研究任务；
- 用户问“PE 是什么”时直接回答，不创建研究任务；
- 用户问“A和B哪个更值得买”时提示当前只支持单标的，并让用户选择一家；
- 用户问“明天会不会涨”时不预测，建议转为分析当前估值和主要风险。

### 5.2 研究对象识别与确认

#### 功能目标

保证所有研究围绕唯一、正确的上市公司实体进行。

#### 产品规则

1. 识别结果至少包含公司名称、证券代码和上市市场；
2. 唯一高置信匹配时可以直接继续，并在研究界面显示研究对象；
3. 同名公司、跨市场上市或品牌与上市主体关系不清时，展示候选项供用户选择；
4. 研究过程中用户明确切换公司时，应创建新任务，原任务不自动混入新任务；
5. 无法确认实体时不得启动正式研究；
6. 已交付结果发现实体错误时，应标记原结果失效并允许用户重新发起正确标的研究。

#### 用户呈现

候选项应提供足够区分信息，例如公司全称、证券代码、市场和主营业务摘要，避免只展示相似名称。

### 5.3 研究范围摘要

#### 功能目标

让用户在任务开始时知道系统准备研究什么，并保留修改方向的能力。

#### 产品规则

1. 完整研究默认覆盖：生意本质、生意质量、护城河、增长与再投资、管理层与资本配置、逆向风险、估值与安全边际；
2. 专项研究只展示与当前问题有关的研究范围；
3. 页面展示概括性的研究问题，不展示模型隐藏推理；
4. 研究计划可以在执行中根据新证据调整；
5. 重要范围变化应在进度中说明，例如“新增客户集中度风险调查”；
6. 用户可以修改研究重点，系统应说明哪些已完成内容继续有效。

### 5.4 研究过程与进度反馈

#### 功能目标

让用户知道任务仍在推进、目前进行到哪里，以及是否需要其参与。

#### 用户可见阶段

- 正在确认公司与研究范围；
- 正在收集公司和行业资料；
- 正在核对财务数据与关键指标；
- 正在调查关键矛盾与风险；
- 正在整理结论与引用；
- 等待用户补充；
- 研究已暂停。

#### 产品规则

1. 进度信息描述正在处理的研究问题和已取得的阶段结果，不展示内部思维链；
2. 长时间任务中不得持续无反馈；推荐初始目标为 60 秒内至少更新一次可见状态，最终阈值由技术验证后确认；
3. 某项数据获取失败时，不应立即将整个任务显示为失败；
4. Agent 可以继续处理不依赖该数据的其他问题；
5. 需要用户作出选择时，任务进入“等待用户”状态，清楚说明为何需要回答；
6. 页面关闭或刷新不应删除已保存的任务和结果。

### 5.5 用户补充、修改、暂停与取消

#### 产品规则

|用户行为|系统行为|
|---|---|
|补充同一公司的资料|核验资料并重新检查受影响的判断|
|增加研究问题|加入当前任务，更新研究范围和预计完成情况|
|改变研究重点|调整未完成工作的优先级，保留仍有效的成果|
|缩小研究范围|停止低优先级工作，按新范围重新判断完成状态|
|切换公司|创建新任务，原任务保持原状态，不混用证据|
|暂停|停止发起新的研究动作，保存已有进度|
|恢复|从未完成问题继续；必要时检查资料是否已过期|
|取消|停止任务，不再生成正式完整报告；保留已产生的用户可见记录|

#### 一致性规则

- 用户最新的明确指令覆盖之前的任务要求；
- 已发出的旧请求晚到时，不得覆盖用户修改后的任务状态；
- 目标改变后，只重新执行受影响的研究，不要求全部从头开始；
- 系统应向用户说明“保留了什么、停止了什么、接下来研究什么”。

### 5.6 研究结果交付

#### 结果结构

完整研究结果采用“结论先行、依据展开”的结构：

1. 研究状态与一句话判断；
2. 当前最关键的研究矛盾；
3. 公司如何赚钱及主要价值来源；
4. 生意质量、护城河、增长和资本配置；
5. 管理层与治理；
6. 关键风险和反证信号；
7. 估值方法、主要假设和隐含预期；
8. 信息缺口与仍需验证项；
9. 引用和数据口径；
10. 可继续追问的问题。

正文目标长度约 1000—1500 字，不作为机械验收条件。研究完整性和可理解性优先于固定字数，详细证据可按需展开。

#### 表达规则

- 事实、计算、估算和判断必须能够区分；
- 关键数字显示数据时点、来源和口径；
- 核心判断同时显示关键依据、成立条件、反证信号和置信度；
- 无可靠证据时允许明确写“暂时无法判断”；
- 不得用“信息不足”掩盖执行故障，应说明是未披露、来源冲突还是获取失败；
- 不以篇幅、章节数量或模型自行声明作为研究完成依据。

#### 条件性交付

估值不是所有任务都必须生成的固定数值。只有存在适用方法和必要数据时，才输出估值分析；条件不足时，应说明无法估值的原因以及需要补充的信息，不得用行业均值或主观数字补齐。

### 5.7 引用与证据查看

#### 产品规则

1. 用户可以从关键判断定位到对应来源；
2. 引用至少显示来源名称、发布日期或报告期、访问时间及相关内容摘要；
3. 社区、访谈和行业观点必须标明其观点属性，不能伪装为公司事实；
4. 多来源口径冲突时并列展示差异和系统采用或不采用的理由；
5. 来源不可再次访问时，历史报告仍保留当时使用的来源记录和必要摘要；
6. 引用存在不代表其必然支持结论，准出前还需要检查引用与结论的对应关系。

### 5.8 追问与续研

#### 产品规则

1. 用户可以围绕结果继续追问；
2. 追问应携带当前公司、已验证证据和研究状态，不要求用户重复背景；
3. 简单解释可以直接回答；需要新增取证时建立续研任务；
4. 续研改变原判断时，应说明新证据和变化原因；
5. 历史报告不静默改写，新结论以更新记录或新版本呈现；
6. 用户从历史记录进入但上下文无法完整恢复时，页面不得宣称已恢复完整研究状态。

### 5.9 候选认知确认

#### 功能目标

将用户认可的、可跨任务复用的判断方法沉淀为个人认知，而不是保存本次公司的临时结论。

#### 候选条件

候选认知应当：

- 有清楚的判断主张；
- 说明适用条件；
- 说明判断逻辑；
- 包含可以推翻或修订它的证据；
- 具备跨公司或跨任务复用价值。

“贵州茅台本季度收入为某个数值”属于任务事实，不属于可复用认知。

#### 产品规则

1. 系统在结果交付后展示少量候选认知；
2. 用户可以确认、修改后确认或拒绝；
3. 未经用户确认的投资认知不得写入个人认知库；
4. 用户跳过认知处理不影响本次报告状态；
5. 用户认知在后续研究中作为待验证假设，不替代新事实；
6. 新证据与用户认知冲突时，应并列展示并由用户决定是否修改认知；
7. 用户可以查看认知来源、编辑、归档和删除。

#### MVP 简化

每次研究建议最多展示 1—3 条候选认知，最终数量通过内测验证。个人偏好静默提取不纳入 P0；在提供明确告知、关闭入口和管理能力前，不应默认扩大自动记忆范围。

### 5.10 历史任务与恢复

#### 产品规则

1. 用户可以查看自己的历史研究和对话；
2. 历史记录至少显示公司、任务类型、创建时间、最终状态和标题；
3. 用户可以重新进入已完成、部分完成、失败或暂停的任务；
4. 恢复任务时应检查关键资料是否已因新财报或时间变化而过期；
5. 过期内容不自动作为当前事实，应提示用户重新核验；
6. MVP 至少保证历史报告可回看；完整跨会话续研属于 P1，未实现时应真实说明能力边界。

### 5.11 能力边界外请求

#### 产品规则

能力边界判断在任务入口和研究过程中均生效。

|请求类型|产品处理|
|---|---|
|涨跌预测|说明不预测涨跌，转为研究估值、市场预期和风险|
|确定性荐股|不替用户作买卖决定，转为呈现支持与反对论点|
|个性化仓位|不提供具体仓位比例，转为说明风险暴露因素|
|全市场选股|说明 MVP 聚焦单标的研究|
|盯盘、提醒、持仓追踪|说明属于后续版本，并可继续研究当前公司|
|非公司类资产|说明当前支持范围，不强行套用公司研究流程|

边界话术应简短、明确，并给用户一个可以继续使用当前产品的替代方向。

## 6. 任务状态与完成标准

### 6.1 用户可见任务状态

|状态|进入条件|用户可进行的操作|退出方式|
|---|---|---|---|
|准备中|正在确认实体和研究范围|修改或取消|开始研究或取消|
|研究中|Agent 正在取证和分析|补充、改重点、暂停、取消|完成、等待用户、暂停或异常|
|等待用户|缺少会改变研究方向的必要信息|回答、修改范围、取消|收到答复后继续|
|已暂停|用户主动暂停或系统暂时不可继续|恢复或取消|恢复研究或取消|
|正在生成结果|研究已停止，正在检查和整理|等待或取消后续认知步骤|生成结果|
|完整完成|约定的核心交付全部满足|查看、追问、确认认知|续研产生新任务或新版本|
|部分完成|已有可用成果，但存在影响交付的缺口|查看缺口、补充资料、继续研究|补齐后完整完成，或维持现状|
|执行失败|系统故障导致最低可用交付也无法形成|重试或稍后继续|重试成功或取消|
|已取消|用户主动终止任务|查看已有记录、重新发起|新建任务|

### 6.2 完整完成标准

完整研究任务同时满足以下条件，才标记“完整完成”：

1. 当前约定范围内的核心问题均已处理；
2. 核心判断具有与之对应的可靠证据；
3. 关键数字有来源、报告期和口径，计算可以复核；
4. 重要反证和风险已被处理或显式说明；
5. 事实、估算、判断和未知没有混淆；
6. 未解决问题不会阻止用户理解主要结论；
7. 结果通过产品规定的硬规则检查。

专项研究以当前专项问题的完成标准判断，不要求机械覆盖完整研究的全部维度。

### 6.3 部分完成标准

满足以下任一情况时，任务应标记“部分完成”：

- 某项核心研究内容因执行故障尚未完成，但其他部分已有可用成果；
- 时间、成本或工具调用预算耗尽；
- 用户缩小范围前已有部分成果，且这些成果仍然有效；
- 关键数据缺失导致某项条件性交付无法生成，但其余结果可用。

部分结果必须说明：已完成内容、未完成内容、原因、对结论的影响及继续研究的方法。

### 6.4 “无法判断”与“执行失败”的区别

- 公开资料未披露、可靠证据不足或证据冲突无法消解，经过合理查证后得出“暂时无法判断”，可以是有效的研究结论；
- 因系统超时、数据服务异常或程序错误而没有完成查证，属于执行缺口；
- 产品不得把执行故障包装为研究结论，也不得把诚实的“无法判断”统一显示为系统失败。

### 6.5 停止原因与结果状态分离

系统停止研究时，必须记录停止原因，例如研究充分、边际收益下降、预算耗尽、等待用户、用户暂停、用户取消或系统异常。停止原因只说明为什么不再执行，最终由准出检查决定交付状态。

## 7. 不确定性、异常与恢复

### 7.1 处理原则

1. 会改变研究对象或核心目标的信息必须向用户确认；
2. 系统能够自行查证的事实不要求用户代为提供；
3. 失败必须显式记录，不能将空结果解释为“没有风险”或“没有披露”；
4. 重试和降级不得降低正确性底线；
5. 局部故障优先局部降级，核心依据缺失时限制结论；
6. 已验证成果应尽可能保存和复用；
7. 所有异常最终都应进入明确状态，不得无限等待或无限重试。

### 7.2 场景处理矩阵

|触发情况|系统处理|用户看到什么|结果状态或下一步|
|---|---|---|---|
|公司存在多个候选|暂停依赖该实体的工作|候选公司和区分信息|等待用户|
|用户未指定研究重点|采用完整研究默认范围|研究范围摘要和修改入口|继续研究|
|非核心数据缺失|继续其他研究，记录缺口|缺失项及影响|可完整或部分完成|
|核心数据未披露|停止依赖该数据的强判断|无法判断的原因及所需信息|有限结论或部分完成|
|来源口径冲突|核对日期、单位、范围，仍冲突则并列保留|冲突内容和结论限制|继续或等待用户|
|单个工具失败|在限制内恢复或换源|必要时提示局部延迟|继续研究|
|多个关键工具失败|保存进度，评估是否还能形成最低交付|故障影响和稍后继续入口|暂停、部分完成或失败|
|模型服务异常|保存任务状态，有限重试|任务暂时中断、进度已保存|暂停或失败|
|任务预算耗尽|停止低优先级工作并整理已有成果|部分结果和缺口清单|部分完成|
|用户长时间未回答必要问题|保持等待并允许从历史入口恢复；保留时长待确认|等待原因和恢复入口|等待或按保留策略关闭|
|用户改变重点|更新范围，只重做受影响内容|范围变更摘要|继续研究|
|用户取消|停止新动作并忽略晚到结果对正式状态的覆盖|已取消及重新发起入口|已取消|

### 7.3 故障后的用户补偿原则

如果未来研究任务涉及次数或费用，系统故障导致的失败不得按完整成功任务计费；具体计费与额度返还规则需在商业化前另行评审。MVP 内测阶段至少应避免因系统自动重试重复消耗用户研究次数。

## 8. 个人认知、隐私与用户控制

### 8.1 数据范围

产品可能保存：

- 用户主动提交的研究问题和资料；
- 研究任务状态、结果和必要运行记录；
- 用户逐条确认的投资认知；
- 为保证服务安全和定位故障所需的审计记录。

### 8.2 用户控制

用户应能够：

- 查看、编辑、归档和删除自己的投资认知；
- 查看历史任务和研究结果；
- 删除允许删除的历史内容；
- 了解哪些个人认知被当前研究引用；
- 纠正错误认知，并使纠正结果优先于旧版本生效。

### 8.3 产品规则

- 未经确认的 Agent 判断不得进入个人投资认知库；
- 认知删除或归档后不得继续注入新研究；
- 用户认知只作为待验证的个人判断框架，不作为事实来源；
- 不同用户之间的研究、认知和历史记录必须隔离；
- 自动偏好记忆上线前必须提供明确告知、关闭入口和管理能力；
- 保存期限、账户删除、数据导出和隐私政策在灰度前形成明确规则。

## 9. 产品指标与验证方案

### 9.1 核心验证目标

MVP 需要分别验证三件事：

1. **研究是否可信：**用户能否追溯关键结论，严重错误是否得到控制；
2. **结果是否有用：**用户能否理解公司的核心逻辑、假设和风险；
3. **认知复用是否有价值：**用户是否愿意确认认知，后续研究中的复用是否帮助其形成判断。

### 9.2 指标分层

|层级|建议指标|说明|
|---|---|---|
|任务交付|研究发起数、完整完成率、部分完成率、失败率、取消率|判断产品是否稳定完成任务|
|研究质量|错实体率、关键数字可追溯率、引用支持率、严重 Bad Case 率|判断结果是否可信|
|体验|首个有效反馈时间、任务耗时、等待用户率、结果展开率|判断过程是否可接受|
|产品价值|结果有帮助率、用户能否说清核心论点与风险、二次研究率|判断研究是否帮助决策过程|
|认知价值|候选认知确认率、修改率、后续引用率、复用有帮助率|验证差异化能力|

追问次数只作为观察信号，不直接等同于产品价值；追问可能来自兴趣，也可能来自报告未讲清楚。

### 9.3 内测验证建议

- 招募符合目标特征的真实用户，使用其正在研究的真实公司；
- 同时覆盖首次完整研究、专项研究、信息不足和失败恢复；
- 记录用户是否理解核心论点、假设、风险和未知；
- 访谈用户对报告长度、等待时间、认知确认负担和复用价值的反馈；
- 将真实任务中的高价值 Bad Case 纳入固定回归集。

## 10. 验收标准

### 10.1 产品功能验收

|编号|给定条件|用户行为|预期结果|
|---|---|---|---|
|AC-01|输入能够唯一匹配上市公司|用户发起完整研究|显示正确公司名称、代码和市场，并建立任务|
|AC-02|输入存在多个候选公司|用户发起研究|展示带区分信息的候选项，确认前不开始正式研究|
|AC-03|用户只查询单个指标|用户提问|直接轻回答，不创建完整研究任务|
|AC-04|用户明确要求研究一家公司|用户提问|建立完整研究任务并展示研究范围摘要|
|AC-05|用户要求比较两家公司|用户提问|说明 MVP 仅支持单标的，并让用户选择一家|
|AC-06|研究正在执行|用户修改重点|系统更新范围，说明保留和重新研究的内容|
|AC-07|研究正在执行|用户切换公司|创建新任务，不将原公司证据写入新任务|
|AC-08|研究正在执行|用户暂停后恢复|已保存成果不丢失，从未完成问题继续|
|AC-09|研究正在执行|用户取消|停止新增动作，任务显示已取消，晚到结果不得覆盖状态|
|AC-10|非核心数据获取失败|系统继续研究|其他部分继续，结果说明缺口及影响|
|AC-11|核心数据未披露|系统完成合理查证|不编造数据，说明无法判断及结论限制|
|AC-12|系统故障导致核心查证未完成|系统停止执行|显示部分完成或执行失败，不显示完整完成|
|AC-13|任务预算耗尽但已有可用成果|系统停止执行|交付部分结果、未完成项和继续方式|
|AC-14|关键数字出现在报告中|用户查看来源|能够查看来源、时点和口径|
|AC-15|估值条件不满足|系统生成结果|说明无法可靠估值，不补造估值数字|
|AC-16|报告生成候选认知|用户不处理|报告仍正常完成，候选认知不入库|
|AC-17|报告生成候选认知|用户确认或修改后确认|认知进入个人库并可以查看、编辑和删除|
|AC-18|历史认知与新证据冲突|系统研究|并列说明冲突，不静默覆盖用户认知或忽略新证据|
|AC-19|用户要求预测涨跌或确定性买卖建议|用户提问|解释能力边界，并引导至估值、论点和风险研究|
|AC-20|用户查看历史任务|用户进入历史记录|看到正确的任务标题、公司、时间、状态和结果|

### 10.2 研究质量验收原则

以下情况属于阻断交付的严重问题：

- 研究对象错误；
- 编造关键财务数字或不存在的来源；
- 引用内容明显不支持对应判断；
- 数据缺失时未经说明直接补值；
- 将社区观点冒充公司事实；
- 输出确定性收益承诺或交易指令；
- 用户之间的任务、历史或认知发生串用；
- 任务实际未完成却显示完整完成。

具体样本数量、自动检查、模型评审和人工抽查比例由《评测与上线方案》定义。

## 11. 体验与非功能要求

### 11.1 响应与等待体验

- 用户提交后应尽快得到已接收和当前处理状态；
- 长时间研究必须持续提供有意义的阶段反馈；
- 总耗时不稳定时不展示虚假精确倒计时；
- 页面刷新、短时断线不应导致已经保存的结果消失；
- 任务完成、等待用户或失败时，应有明确可见状态；是否提供站外通知由后续版本决定。

响应时间、完整研究 P50/P95 耗时和单任务成本，在技术验证后填写为可验收门槛。推荐先使用“首个有效反馈”和“持续无反馈时长”衡量等待体验，而不是承诺不可靠的完成倒计时。

### 11.2 可理解性

- 结论先行，专业术语在首次出现时提供简短解释；
- 结果不能只给指标，要解释指标与研究判断的关系；
- 置信度必须和具体原因一起出现，不能只展示一个分数；
- 错误和缺口提示说明用户可以如何继续。

### 11.3 可访问性与兼容性

- 关键状态和结论不能只依靠颜色区分；
- 交互控件支持键盘操作和清晰焦点；
- 引用、确认和取消等关键操作有明确文本；
- 首发支持的浏览器和移动端策略在设计评审前确认。

## 12. 依赖、风险与待验证事项

### 12.1 关键依赖

|依赖|影响|需要的验证|
|---|---|---|
|证券实体主数据|决定研究对象是否正确|覆盖 A 股和港股常见名称、代码及跨市场情况|
|财务与行情数据源|决定指标和估值能否交付|字段覆盖、口径、稳定性和失败率|
|公告、财报和网页检索|决定非结构化证据质量|可访问性、解析成功率和引用能力|
|大模型服务|决定规划、提取和表达质量|真实端到端稳定性、耗时和成本|
|任务状态与历史存储|决定暂停、恢复和追溯|断线、刷新、异常和用户隔离|
|行业研究资产|决定不同公司研究深度|首批四类行业的覆盖和适用性|

### 12.2 主要产品风险

|风险|产品影响|产品措施|
|---|---|---|
|研究对象识别错误|整份报告误导用户|歧义确认、结果页持续显示实体、错误报告失效|
|报告专业但用户看不懂|核心价值无法实现|结论先行、解释指标与判断的关系、用户测试|
|报告太长且重点不清|用户无法形成判断|突出核心矛盾，详细证据按需展开|
|信息不足仍给出强结论|损害可信度|限制结论、展示缺口和反证|
|用户认知强化原有偏见|形成错误的个性化|认知作为待验证假设，必须接受新证据检验|
|认知确认负担过重|用户跳过核心差异化功能|限制候选数量，验证卡片内容和时机|
|研究耗时和成本过高|无法规模化|任务分级、预算控制、专项研究和部分交付|
|失败后任务无结果|用户失去信任|保存进度、局部降级、明确状态和恢复入口|

### 12.3 待技术验证事项

1. A 股、港股关键字段的真实覆盖率；
2. 一次完整研究的 P50/P95 耗时和成本；
3. 页面关闭、断线和服务重启后的任务恢复能力；
4. 引用内容与结论是否支持的检查方式；
5. 多来源口径冲突的识别能力；
6. 任务取消后晚到结果的隔离能力；
7. 首批行业以外使用通用框架时的质量下限。

## 13. 版本计划

|阶段|目标|主要内容|进入下一阶段条件|
|---|---|---|---|

## 15. 原型要求与文档对应关系

### 15.1 原型入口

完整可交互原型链接放在本文档首页，并标注原型版本、对应 PRD 版本和更新时间。

### 15.2 PRD 中的原型呈现
