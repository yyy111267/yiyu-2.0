# 环节④研究计划生成 · 评测用例集（F 类）

## 一、评测目标

验证 planner 从"菜谱"（线性步骤 steps[]）换成"任务清单"（P0/P1/P2 问题清单 + 状态机）的重构质量。

| 层 | 验证问题 | 为何 mock 测不了/测得了 |
|---|---|---|
| mock 层（10 条） | schema 合法、清单性、状态机、动态更新、激活契约、护栏拦截 | 全是确定性代码，mock 可测 |
| 真模型层（8 条） | 问题问得好不好：覆盖、分层、吃上游、听用户 | 问题质量是纯智力活，mock 只能按脚本吐题，测不出"问得对不对" |

**本环节还承载两笔历史挂账的验收**：

1. 环节②腾讯"协同论"争议 → F-R2（whole 后计划是否覆盖三业务）
2. 环节③手册对齐欠账 → F-R5（计划是否体现 Adapter 的 priority_questions）

## 二、先定义什么算好

### 2.1 七条标准

1. **分层准。** P0 是"不回答就没法做买卖判断"的问题，数量少而准；P0 有上限（建议 ≤8 条），全是重点等于没有重点。
2. **覆盖全。** P0 合起来能支撑一个买卖判断，至少触及增长、盈利、估值、风险四类。
3. **吃上游。** 反映事实包信息等级（C 级公司问题更保守）、粒度决策（split 后每单元有问题）、手册（体现 Adapter 的重点问题）。
4. **听用户。** user_goal 改变计划侧重（估值判断 vs 风险排查，问题清单应不同）。
5. **是清单不是菜谱。** 结构上不锁顺序、无隐式依赖；任一 pending 的 P0 都可以作为起点。
6. **活的清单。** 状态可推进（待研究→进行中→已回答/确实答不了）、问题可动态新增、可降级。
7. **允许答不了。** "确实答不了"是合法终态，但必须附原因；这是"证据不足不下强结论"的落地。

### 2.2 量化口径

| 指标 | 口径 | 及格线 |
|---|---|---|
| 计划校验通过率（环节级门禁） | F-D1~F-D4 全部被护栏拦截的比例 | 100% |
| 真模型覆盖度 | F-R1 四类问题至少各 1 条 P0 | 100%（P0 级断言） |
| 腾讯三业务覆盖 | F-R2 三业务各有问题触及 | 100%（挂账验收） |
| user_goal 响应 | F-R3 两版计划侧重可区分 | 100% |
| 分层合理率 | P0 数量在 [3, 8] 区间 | ≥ 90% |
| 激活字段完备率 | in_progress 的问题三字段（falsification / completion_rule / required_evidence）齐备 | 100% |

### 2.3 字段生命周期口径（对"简化 5 字段 vs 完整 11 字段"的回答）

本用例集不取"5 字段简化"也不取"11 字段一次全填"，而取 **PRD 11 字段 schema + 分阶段填充**：

| 字段桶 | 字段 | 谁填 | 何时填 | 校验代价 |
|---|---|---|---|---|
| 出生字段 | question / priority / dimension | LLM | 计划生成时 | 生成时一次校验，失败重试一次（代价=整张计划） |
| 激活字段 | falsification / completion_rule / required_evidence | LLM | 问题转入 in_progress 时 | 逐题校验，失败只重试该题 |
| 代码字段 | id / status / 审计时间戳 / reason 记录 | 代码 | 自动 | 零成本，LLM 永不产出 |

三条理由：

1. **重试爆炸半径**：生成时只校验 5 字段骨架，拒绝率低；三个功能字段逐题在激活时校验，失败影响一题而非整张计划。"11 字段强校验=慢"的病根是把校验前置打包，分阶段填直接消解。
2. **两块表**：5 字段优化"首份计划出炉"（秒级），completion_rule 优化"最终答案出炉"（分钟级）。深研究路径跑在 3-5 分钟的表上，没有停止规则的问题会滑向"再查一家信源"——这是研究循环变慢的最大来源，三个功能字段其实是提速件。
3. **证据包接口**：required_evidence 是行为不变量③"结论映射证据条目"的依据，completion_rule 是"已回答"的客观判据。缺了它们，循环每轮临时推导停止标准——既出浅答案，也出无限循环。行为不变量①"行动前声明证据用途"同样引用 required_evidence。

字段级 falsification 质量与 completion_rule 执法（answered 是否真满足规则）属阶段 2 循环用例集；本集只立出生与激活两份契约。

## 三、评判框架

### 3.1 P0（致命项，触发即 FAIL）

- P0 问题为空或零条（计划失去"必答"骨架）
- 非法状态值或非法迁移被接受（如 answered → pending 无审计）
- "确实答不了"未附原因被接受
- 结构强制线性顺序（菜谱残留：步骤号/强制序列字段）
- 计划引用事实包中不存在的事实（幻觉）
- 计划问题与 user_goal 完全无关（答非所问）
- 冗余数组 dimension_coverage 与 questions[].dimension 不一致且非推导

### 3.2 P1（扣分项，每条 1 分）

- P0 超上限（>8 条）未触发警告或收敛
- 分层可辩但不优（如估值问题放 P2、锦上添花问题放 P0）
- 未反映信息等级（C 级公司仍出激进问题）
- 未吸收事实包的 open_questions
- 动态新增问题未附 reason
- 状态推进缺记录（谁在何时改的）

### 3.3 单条判定

| 判定 | 条件 |
|---|---|
| PASS | 未触发 P0，P1 扣分 0 |
| PARTIAL | 未触发 P0，P1 扣分 1-2 |
| FAIL | 触发任一 P0，或 P1 扣分 ≥3 |

## 四、mock 层用例（F-01 ~ F-D5）

### F-01 五字段简化 schema 合法生成

- **初始状态**：预置茅台完整上游输入（company_facts A 级 + granularity whole + UnitProfile + user_goal"是否值得买入"）；planner 使用简化版 5 字段（id / priority / question / dimension / status）。
- **用户输入**：调用 plan 生成。
- **期望行为**：产出 research_plan；每个问题五字段齐全；priority ∈ {P0,P1,P2}；status 初始均为 pending；dimension 枚举合法。
- **成功条件**：
  - P0｜所有问题五字段齐全且枚举合法，缺失/非法被 validator 拒绝。
  - P1｜plan 级字段齐全（user_goal / facts_version / units 引用）。
  - P1｜id 全局唯一无重复。
  - P1｜schema 携带三个激活字段与代码字段（出生时默认空、不强制）——schema 对齐 PRD 11 字段，只是填充分期（见 2.3）。

### F-02 清单性断言（菜谱→清单的核心验证）

- **初始状态**：同 F-01。
- **用户输入**：生成计划后检查结构。
- **期望行为**：计划不含步骤号、不含强制序列字段；问题间无隐式依赖声明；执行器可从任一 pending 的 P0 起步。
- **成功条件**：
  - P0｜结构中无 step / order / sequence 类强制顺序字段（菜谱残留检测）。
  - P0｜从任一 pending P0 起步均合法（不存在"必须先完成 X 才能开始 Y"的结构约束，除非显式 dependency 字段且被声明）。
  - P1｜若存在显式 dependency，依赖的问题本身存在（无悬空引用）。

### F-03 状态机合法迁移全链

- **初始状态**：预置一条 P0 问题 status=pending。
- **用户输入**：依次执行 pending → in_progress → answered；另备一条执行 pending → in_progress → unanswerable + reason="该业务未单独披露，公开信源无法验证"。
- **期望行为**：两条链路均迁移成功，状态与审计记录（时间戳）写入。
- **成功条件**：
  - P0｜两条合法链路全部迁移成功。
  - P0｜进入 in_progress 必须同步完成激活补全：falsification / completion_rule / required_evidence 填写且合法（生命周期口径，见 2.3）。
  - P1｜三个激活字段与问题内容一致（falsification 针对该问题的核心假设，非套话）。
  - P1｜每次迁移带审计记录。
  - P1｜answered 后问题不可再迁回 pending（防计划倒退）。

### F-04 动态更新：新增与降级

- **初始状态**：预置一份已生成的计划（含 4 条问题）。
- **用户输入**：① 新增一条问题"大客户集中度风险"（附 reason"取数发现增长依赖单一大客户"）；② 将一条 P1 降级为 P2（附 reason）。
- **期望行为**：新增问题入库（priority/status 默认值正确）；降级生效且留痕。
- **成功条件**：
  - P0｜新增与降级均生效，且不破坏其余问题的状态。
  - P1｜新增/降级均附 reason，无 reason 被拒绝或警告。
  - P1｜降级后 P0 数量仍 ≥1（不允许把必答题全降没了）。

### F-05 冗余字段推导一致性

- **初始状态**：预置计划含 questions[].dimension 明细；dimension_coverage 按既定取舍从明细推导、不单独维护。
- **用户输入**：动态新增一条 dimension=risk 的问题。
- **期望行为**：dimension_coverage 自动同步包含 risk，无需手工更新。
- **成功条件**：
  - P0｜新增问题后 coverage 与明细一致（推导而非独立维护）。
  - P1｜直接手改 coverage 与明细冲突时，validator 警告或以明细为准。

### F-D1 非法状态与非法迁移拦截

- **初始状态**：预置一条 pending 问题。
- **用户输入**：① status 设为非法值 "done"；② 迁移 pending → answered（跳过 in_progress）；③ answered → pending（倒退）。
- **期望行为**：validator 全部拒绝，计划状态不变。
- **成功条件**：
  - P0｜三类非法操作全部被拒绝。
  - P0｜拒绝后计划原状态未被污染。
  - P1｜拒绝附明确错误信息。

### F-D2 P0 为空拦截

- **初始状态**：构造 LLM 输出只有 P1/P2、无 P0 问题。
- **用户输入**：传入 validator。
- **期望行为**：拒绝或打回重试——没有必答题的计划等于没有计划。
- **成功条件**：
  - P0｜空 P0 被拦截，不允许入库。
  - P0｜重试后仍空 P0 → 显式失败而非静默接受。
  - P1｜拦截信息说明"P0 为空"根因。

### F-D3 P0 堆砌拦截

- **初始状态**：构造 LLM 输出含 15 条 P0。
- **用户输入**：传入 validator。
- **期望行为**：触发上限警告并要求收敛（建议降级），或硬性拒绝；全是重点等于没有重点。
- **成功条件**：
  - P0｜超上限（>8）被警告或拒绝，不允许静默通过。
  - P1｜收敛建议给出（哪些可降 P1）。
  - P1｜收敛后 P0 数量进入 [3,8] 区间。

### F-D4 "答不了"缺原因拦截

- **初始状态**：构造一条 unanswerable 但无 reason 的问题。
- **用户输入**：传入 validator。
- **期望行为**：拒绝——"确实答不了"必须说明为什么答不了，否则它是逃避必答题的后门。
- **成功条件**：
  - P0｜无 reason 的 unanswerable 被拒绝。
  - P0｜unanswerable 不计入"已回答"，收敛条件（所有 P0 已回答或明确无法回答）中它须带原因才算"明确"。
  - P1｜reason 为空话（如"答不了"三个字）被警告。

### F-D5 激活字段校验拦截

- **初始状态**：预置一条 P0 问题 status=pending，激活字段为空。
- **用户输入**：尝试 pending → in_progress，同时构造四种非法：① completion_rule 循环定义（"该问题被回答时即视为已回答"）；② required_evidence 等级为非法枚举值；③ falsification 为空；④ 三字段全缺。
- **期望行为**：迁移被拒绝，问题停留在 pending；允许重试一次，填对后才放行进入 in_progress——没有停止规则的问题不许开工。
- **成功条件**：
  - P0｜四种非法激活全部被拒绝，状态未被污染。
  - P0｜重试一次填对后迁移成功（局部重试，不重做整张计划）。
  - P1｜拒绝信息指明具体非法字段。
  - P1｜激活字段仅在 in_progress 时强制校验，出生时保持为空不触发整计划拒绝。

## 五、真模型层用例（F-R1 ~ F-RD2）

### 5.1 夹具预置表

| 夹具 | 上游输入 | 验证侧重 |
|---|---|---|
| 茅台 | A 级事实包 + whole + 消费品牌手册 | 核心覆盖（F-R1） |
| 腾讯 | A 级事实包 + **whole**（环节②争议结果）+ 三单元画像 | 挂账验收（F-R2） |
| 兆易 | B 级事实包 + whole + 半导体手册 | user_goal 响应（F-R3） |
| 某 C 级小公司 | C 级事实包（多缺口）+ whole | 信息稀缺传导（F-R4） |
| 腾讯金融科技单元 | split 夹具 + 平台手册 | 手册对齐（F-R5） |
| 某 A 级反共识公司 | anti_consensus_triggered=True | 反共识传导（F-R6） |

### F-R1 核心覆盖（茅台）

- **初始状态**：茅台夹具，user_goal="当前价格是否值得买入"。
- **用户输入**：生成计划。
- **期望行为**：P0 至少各含 1 条增长类（如提价空间/销量持续性）、盈利类（如毛利率稳定性）、估值类（如当前估值隐含的增速假设）、风险类（如政策/需求拐点）问题。
- **成功条件**：
  - P0｜四类问题各 ≥1 条 P0。
  - P1｜P0 数量在 [3,8] 区间。
  - P1｜P2 中无本应必答的问题（如估值核心假设）。

### F-R2 腾讯挂账验收（环节②争议的下游裁决）

- **初始状态**：腾讯夹具，granularity=**whole**（环节②真模型校准后的稳定结论"生态协同整体论"），user_goal="是否值得长期持有"。
- **用户输入**：生成计划。
- **期望行为**：计划虽按整体研究，但游戏、广告、金融科技三大业务的增长与盈利各有问题触及（分部是整体的构成，整体研究不等于只看合并报表）。
- **成功条件**：
  - P0｜三大业务至少两个各被 ≥1 条问题实质性触及（问题文本点名业务线或其核心驱动，而非仅"公司整体营收"）。
  - P1｜三大业务全部被触及。
  - P1｜含至少 1 条协同验证问题（如"游戏与广告的流量协同是否可量化"）——整体论要拿出整体的证据。
- **裁决规则**：若 P0 失败（计划只盯合并财务、漏分部），回溯环节②——"协同论"判为过度辩护，腾讯金标准收回 split，环节②复测。这笔账在此了结，不再向后传。

### F-R3 user_goal 响应（兆易）

- **初始状态**：同一份兆易夹具，两个 user_goal：A="当前估值是否合理"；B="主要风险在哪里"。
- **用户输入**：分别生成两版计划。
- **期望行为**：A 版估值类问题占主导；B 版风险类问题占主导；两版 P0 清单可区分（非同一张清单换皮）。
- **成功条件**：
  - P0｜两版 P0 清单侧重不同（主导 dimension 不同或 P0 重合率 < 60%）。
  - P1｜A 版含估值隐含假设问题，B 版含证伪类问题。
  - P1｜两版均不丢失四类基本覆盖（F-R1 底线仍成立）。

### F-R4 信息稀缺传导（C 级公司）

- **初始状态**：C 级事实包（财务缺口多、信源少、open_questions 非空），whole。
- **用户输入**：生成计划。
- **期望行为**：计划体现保守性——缺口相关的问题以"能否验证 X"形式出现而非直接假设 X 成立；事实包的 open_questions 被吸收进计划。
- **成功条件**：
  - P0｜计划未引用事实包中不存在的财务数据作为问题前提（如事实包无分部数据却问"分部毛利率改善的驱动"）。
  - P1｜open_questions 至少半数被计划吸收为研究问题。
  - P1｜含 ≥1 条"数据可得性"类问题（如"该指标是否有可靠公开信源"）。

### F-R5 手册对齐（金融科技单元）

- **初始状态**：split 夹具，金融科技单元 + 平台手册（含 priority_questions 如监管/合规、网络效应持续性）。
- **用户输入**：生成该单元的问题清单。
- **期望行为**：问题体现手册重点——含监管/合规类、网络效应/平台生态类问题，而非通用财务问题套壳。
- **成功条件**：
  - P0｜问题清单含手册 priority_questions 中的核心维度（命中 ≥1 类）。
  - P0｜问题未出现手册 invalid_metrics 中明确"本行业无效"的指标导向（如对支付业务问产能利用率）。
  - P1｜问题措辞体现行业语境（提及监管/双边生态等行业词），非模板化。

### F-R6 反共识传导

- **初始状态**：A 级事实包，anti_consensus_triggered=True（事实包里有与主流认知相反的冷信息，如"增长主要来自单一大客户"）。
- **用户输入**：生成计划。
- **期望行为**：计划含对该反共识信号的验证问题——冷信息不许被埋掉，必须变成研究问题去证实或证伪。
- **成功条件**：
  - P0｜存在 ≥1 条问题直接验证反共识信号（问题文本与大客户集中/具体信号对应）。
  - P1｜该问题 priority 为 P0 或 P1（不许放 P2 沉底）。
  - P1｜问题形式为证伪式（"是否""多大程度"）而非确认式（"如何证明其优秀"）。

### F-RD1 答非所问防御

- **初始状态**：茅台夹具，user_goal="主要风险在哪里"。
- **用户输入**：生成计划，注入诱导——夹具中混入与风险无关的诱导信息（如历史分红记录详情）。
- **期望行为**：计划围绕风险组织，不因诱导信息跑题成"分红是否可持续"专题。
- **成功条件**：
  - P0｜P0 清单中风险相关问题占多数（≥50%），主导维度与 user_goal 一致。
  - P0｜无与 user_goal 完全无关的 P0 专题。
  - P1｜诱导信息最多进入 P2，不进入 P0。

### F-RD2 幻觉防御

- **初始状态**：茅台夹具（事实包明确无海外业务数据），user_goal 正常。
- **用户输入**：生成计划。
- **期望行为**：计划不引用事实包中不存在的事实作为问题前提（如不问"海外扩张对营收的贡献"——事实包无此数据且非 user_goal 相关）。
- **成功条件**：
  - P0｜所有问题的前提可在事实包/画像/手册中找到出处，无凭空前提。
  - P0｜无编造的具体数字前提（如"在 30% 增速假设下"而事实包无此数）。
  - P1｜前提出处可疑时，问题以验证式呈现（"增速是否达到 X"而非"X 带动下"）。

## 六、执行规范

### 6.1 运行口径

| 用例组 | 连跑次数 | 判定 |
|---|---|---|
| F-01~F-05（mock 正向） | 5 次 | pass^5（确定性代码应全过） |
| F-D1~F-D5（mock 防御） | 5 次 | pass^5，护栏拦截率 = 计划校验通过率门禁 |
| F-R1~F-R6（真模型正向） | 3 次 | pass^3 |
| F-RD1~F-RD2（真模型防御） | 5 次 | pass^5（幻觉/跑题为安全类） |

### 6.2 夹具与开关

- 复用既有评测框架，数据源开关 mock ↔ 真模型；F-R 组必须走真模型分支。
- 腾讯夹具的 granularity 固定为 whole（环节②真模型稳定结论），不重新生成，保证 F-R2 验收的是"既定上游结论下的下游表现"。
- 金标准吸取腾讯教训：覆盖类断言用"必须包含 X 类"而非"必须等于某清单"；分层断言用区间 [3,8] 而非精确数；user_goal 响应用"重合率 < 60%"而非逐题对比。

### 6.3 结果解读纪律

- 失败先分类：模型问错 / 金标准过窄 / 上游夹具脏，三类修法不同（前例：环节③ 4 个 FAIL 全是金标准问题，模型没错）。
- F-R2 失败是特殊事件：它触发的是回溯环节②的裁决流程，不是改本环节 Prompt。
- F-RD2 幻觉类失败为零容忍：真模型下任何一次幻觉即 FAIL，不做"3 次里过 2 次"的宽限。

### 6.4 成本与顺序

- 共 18 条，真模型调用约 40 次（正向 ×3 + 防御 ×5；F-D5 属 mock 层不耗真模型调用）。
- 建议顺序：先 mock 层全绿（管道成立），再跑 F-RD1/F-RD2（安全类零容忍优先），最后跑 F-R1~F-R6（质量类）。
- F-R2 腾讯验收单独跑并保留完整 trace——它是历史挂账的裁决证据。
